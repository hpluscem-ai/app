# React Native 개발 기록

## 2026-08-14 — 로그인 화면

- 목표: Figma 로그인 화면을 WebView 없이 React Native 컴포넌트로 구현한다.
- 사용한 개념: Expo Router `Stack`, Safe Area, `KeyboardAvoidingView`, `ScrollView`, `TextInput`, `Pressable`, `StyleSheet`.
- 네이티브 화면 구성: HTML과 CSS 대신 `View`, `Text`, `Image`, `TextInput`을 조합하고 iOS·Android가 공통으로 해석하는 스타일을 작성했다.
- 모바일 환경 대응: 상태 표시줄과 홈 인디케이터의 안전 영역, 소프트 키보드, 작은 화면의 세로 스크롤을 고려했다.
- 입력 UX: 이메일 키보드의 Next로 비밀번호에 포커스를 옮기고, Done 또는 로그인 버튼으로 검증하며, 최초 오류 입력에 다시 포커스한다.
- 폼 상태 관리: React Hook Form의 `useForm`과 `Controller`로 React Native `TextInput`을 연결했다. 첫 제출 전에는 검증 메시지를 노출하지 않고, 제출 후 오류가 있는 입력은 변경할 때 다시 검증한다.
- 공용 입력 규칙: 이메일·비밀번호·휴대폰 검증은 `utils/validation.ts`, `010-0000-0000` 포매팅은 `utils/inputFormat.ts`로 분리해 회원가입과 계정 찾기 화면에서 재사용할 수 있게 했다.
- 디자인 토큰과 소스: 공용 색상·타이포그래피는 `constants/theme.ts`, 이미지와 SVG 경로는 `constants/assets.ts`에서 관리해 화면 코드에 원시 값을 반복하지 않게 했다.
- 에셋 처리: Figma에서 내려받은 원본 로고를 앱 에셋으로 저장하고 화면과 푸터에서 크기만 달리해 재사용했다.
- AI 지원: Figma 노드와 기획 설명 분석, Expo SDK 57 문서 확인, 구현 초안과 검증 항목 정리를 지원했다.
- 개발자 판단: 공용 앱바만 별도 컴포넌트로 두고 로그인 화면 전용 UI·상태·검증은 한 파일에서 리뷰할 수 있게 유지했다. 서버가 없는 상태에서 가짜 로그인 성공이나 토큰을 만들지 않았다.
- 개발자 피드백 반영: 헤더를 공용 앱바로 분리하고 React Native Paper를 사용했으며, 제공된 SVG를 뒤로가기 아이콘으로 적용했다. 이전 화면이 없으면 버튼을 숨긴다.
- 검증 결과: `pnpm typecheck` 통과. 휴대폰 번호의 빈 값·부분 입력·완성 입력·기호 포함 붙여넣기 등 포매팅 7개 사례와 `010` 검증을 실행해 통과했다. Expo public config에서 SDK `57.0.0`과 `expo-router` plugin을 확인했다. iPhone 16 Plus(iOS 18.5) 시뮬레이터에서 앱바, 로고, 52px 입력·버튼, 반응형 가로 폭과 푸터 시작 위치를 Figma와 비교했고, 디자인 토큰·에셋 소스 분리와 React Hook Form 전환 후에도 동일하게 렌더링되는 것을 재확인했다. Android 기기 및 키보드가 열린 오류 입력 흐름은 아직 검증하지 않았다.
- 이력서 근거: React Native와 Expo Router 기반 크로스플랫폼 로그인 UI, 네이티브 입력 흐름, 반응형 스크롤 및 클라이언트 검증을 구현했다.
- 성능 및 생산성 수치: `[측정 필요]`.

- 서버 경계: 소속 목록, 이메일·연락처 중복 확인, 카카오톡 인증번호 발송·재발송·만료, 인증번호 검증과 계정 생성은 가짜 성공 상태를 만들지 않고 서버 계약 대기 상태로 남겼다.
- 검증 결과: `pnpm typecheck` 통과. iPhone 16 Plus(iOS 18.5) 시뮬레이터에서 앱바, 로고, 입력 7개, 연락처·발송 버튼 행, 약관 3개, 가입 버튼과 스크롤 레이아웃을 Figma와 비교했다.

## 2026-08-15 — 인증 화면 공용 UI 리팩터링

- 목표: 로그인과 회원가입에서 실제로 중복된 푸터, 입력 필드, 버튼, 화면 틀을 공용 컴포넌트로 옮기고 각 화면에는 폼 검증과 이동 로직만 남긴다.
- React Native 구성: `AuthScreen`이 Safe Area, 키보드 회피, 네이티브 스크롤, 브랜드 영역과 푸터 배치를 담당한다. 웹의 공통 페이지 레이아웃과 역할은 비슷하지만 브라우저 DOM 대신 `SafeAreaView`, `KeyboardAvoidingView`, `ScrollView`의 플랫폼 동작을 캡슐화했다.
- 공용 컴포넌트: `AppFooter`는 고정 콘텐츠, `FormTextField`는 React Hook Form에서 전달받은 값·ref·오류 표시, `PrimaryButton`은 너비·비활성·누름 시각 상태만 담당한다.
- 인증 경계: `AuthScreen`과 `PrimaryButton`에는 세션, API 요청, 토큰 또는 로딩 상태를 넣지 않았다. 서버 계약이 정해지면 각 화면의 제출 함수에서 요청을 연결하고 필요한 상태만 props로 확장할 수 있다.
- AI 지원: 두 화면의 중복과 차이를 대조하고 최소 props 후보, 접근성 및 시각 회귀 점검 항목을 정리했다.

## 2026-08-15 — 입력 검증과 안내창 관리

- 목표: 화면 안에 반복되던 검증 함수와 `Alert.alert` 호출을 이름 있는 공용 함수로 옮기고, 한 번만 쓰이던 `LoginForm`·`SignUpForm` 컴포넌트 계층을 제거한다.
- 검증 구조: 정규식과 이메일·비밀번호·휴대폰 검증 메시지는 `utils/validation.ts`, 입력값 변환은 `utils/inputFormat.ts`에서 각각 관리한다. 화면의 React Hook Form `rules`에는 공용 검증 함수만 전달한다.
- 안내창 구조: `utils/alerts.ts`에 현재 네 개의 단순 안내창을 모았다. 인증 전용 파일명으로 제한하지 않아 이후 다른 화면의 공통 Alert도 같은 위치에서 관리할 수 있다.
- 컴포넌트 구조: 인증 기능이 없는 공용 버튼은 역할에 맞게 `PrimaryButton`으로 이름을 변경했다. 각 Expo Router 라우트가 `useForm`과 `AuthScreen`을 직접 소유해 불필요한 한 단계 렌더링 계층을 제거했다.
- AI 지원: 공용 함수의 책임 경계와 이름 후보, 기존 오류 메시지·접근성·React Hook Form 동작을 유지하는 검증 항목을 정리했다.
- 개발자 판단: 앱 전역 안내창 확장을 고려해 `authAlerts.ts` 대신 `alerts.ts`를 선택했다. 서버 오류 계약과 세션 상태는 아직 정해지지 않았으므로 이번 유틸에 포함하지 않았다.
- 검증 결과: `pnpm typecheck`, 코드 형식 검사, 이메일·비밀번호·휴대폰 검증과 전화번호 포매팅 사례를 통과했다. iPhone 16 Plus(iOS 18.5) 시뮬레이터에서 로그인과 회원가입 화면이 구조 변경 전과 동일하게 렌더링되는 것을 확인했다. Android 실기기와 키보드가 열린 상태는 아직 검증하지 않았다.

## 2026-08-15 — 이메일·비밀번호 찾기와 비밀번호 재설정 화면

- 경로: Figma 기획의 `/find-email`, `/find-password`, `/reset-password`를 Expo Router의 같은 이름 파일로 구현하고 로그인 화면의 이메일·비밀번호 찾기 메뉴를 연결했다.
- 공용 화면 구조: 세 화면 모두 기존 `AuthScreen`, `FormTextField`, `PrimaryButton`, `AppFooter`, `AppBar`를 조합했다. 각 라우트에는 그 화면의 입력값, React Hook Form 규칙, 결과 표시와 이동만 남겼다.
- 이메일 찾기: 연락처를 `010-0000-0000` 형식으로 자동 변환하고 숫자 6자리 인증번호를 검증한다. 실제 서버가 인증 증명과 조회 결과를 반환하기 전에는 결과 화면으로 전환하지 않는다.
- 비밀번호 찾기: 이메일 형식, 연락처와 인증번호를 검증한다. 실제 서버가 본인 확인과 재설정 링크 발송에 성공하기 전에는 완료 결과를 표시하지 않는다.
- 비밀번호 재설정: 영문·숫자·특수문자를 포함한 8자 이상 새 비밀번호와 확인값 일치를 실시간으로 검증한다. 재설정 Token 검증과 저장 성공 전에는 완료 상태를 만들지 않는다.
- 기획 반영: Figma 화면 문구의 비밀번호 `6자리` 예시보다 상세 기획의 `8자 이상` 정책과 기존 로그인·회원가입 정책을 우선했다. 재설정 링크 만료 시간이 `미정`과 `24시간`으로 함께 적혀 있어 서버 정책 결정 항목으로 남겼다.
- 서버 경계: 카카오톡 인증번호 발송·재발송·만료, 인증번호 확인, 이메일 조회, 재설정 링크 발송, Token 검증과 비밀번호 저장은 가짜 성공으로 처리하지 않는다. 현재 제출은 클라이언트 검증 후 서버 연동 대기 안내만 표시한다.
- 단순성 판단: 세 화면에서 실제로 반복되는 연락처·인증번호 두 행만 `PhoneVerificationSection`으로 공용화했다. 화면마다 다른 발송 선행 조건과 최종 제출은 각 라우트에 유지했고, 서버 계약 전에는 별도 Hook이나 서비스 계층을 만들지 않았다.
- AI 지원: Figma의 화면과 기획 설명을 함께 분석하고, Expo SDK 57 라우팅 방식, 입력 접근성, 서버 경계와 시각 비교 항목을 정리했다.
- 검증 결과: `pnpm typecheck`와 `git diff --check`를 통과했다. iPhone 16 Plus(iOS 18.5) 시뮬레이터에서 이메일 찾기, 비밀번호 찾기와 비밀번호 재설정 입력 화면의 앱바, 로고, 입력·버튼과 푸터를 Figma와 비교했다. Android 실기기, 키보드가 열린 오류 흐름과 실제 서버 응답은 아직 검증하지 않았다.
- 이력서 근거: React Native와 Expo Router로 계정 복구 UI를 구현하고, 공용 네이티브 컴포넌트와 화면별 폼 상태를 분리했으며, 미정인 서버 인증 흐름을 명시적인 경계로 유지했다.

## AUTH-001 로그인

- 상태: 2026-09-06 세션 DB와 v1→v2 마이그레이션, 로그인·세션 확인·로그아웃 API, 만료 검사와 소속 비활성화 시 기존 세션 폐기까지 구현했다. 2026-09-07 현재 비밀번호 확인을 통한 변경 API를 추가했다. 앱 연동과 이메일 링크 기반 찾기·재설정 API는 아직 미구현이다. 2026-09-05 사용자 결정으로 아래 기사 앱 세션 유지기간·로그아웃·로그인 제한 정책을 확정했으며 어드민 정책은 별도다.
- 1차 저장 구조: 서버의 `auth_sessions`는 `token_hash`, `user_id`, `created_at`, `last_used_at`, `expires_at`만 저장한다. SHA-256 해시를 기본키로 사용하고 사용자별 인덱스는 중복을 허용해 다중 기기 세션을 지원한다. 토큰 원문 저장 컬럼은 없다.
- 시각 타입: 새 세션 시각은 SQLite STRICT 테이블에서 UTC Unix 밀리초 정수로 저장하고 Drizzle의 `timestamp_ms`로 `Date` 타입에 매핑한다. 기존 테이블의 시각 저장 형식은 변경하지 않았다. 참고: [Drizzle SQLite 날짜 매핑](https://orm.drizzle.team/docs/sqlite/column-types#integer).
- 마이그레이션: 기존 v1 `schema.sql`은 유지하고 `002-auth-sessions.sql`에서 세션 테이블·제약·인덱스만 추가한다. 새 DB는 v1 생성 후 v2까지 적용하고, 기존 v1 DB는 데이터와 기존 스키마를 보존하며 v2로 갱신한다. 실패한 마이그레이션은 롤백하고 이미 v2인 DB에는 다시 실행하지 않는다.
- 1차 검증: 테스트 우선 방식으로 신규 테이블·기존 데이터 보존·롤백 테스트가 변경 전 코드에서 실패하는 것을 확인한 뒤 구현했다. 단위 테스트 17개, 기존 E2E 54개, 서버 타입 검사·빌드·ESLint·빌드된 DB 서비스의 세션 스키마 생성 검사를 통과했다. 자체 코드리뷰에서 마이그레이션 범위·참조 제약·날짜 왕복 변환·테스트 자원 정리를 점검했다. 새 API가 없으므로 Swagger는 변경하지 않았고 실제 사용자 DB에는 마이그레이션을 직접 실행하지 않았다.
- 2차 로그인 API: `POST /api/v1/auth/login`은 `{ email, password }`를 받아 `{ token, expiresAt }`를 HTTP 200으로 반환한다. 이메일만 공백을 제거하고 대소문자를 구분하지 않으며 비밀번호 원문은 변경하지 않는다. 기사 계정만 허용하고 어드민 계정에는 세션을 발급하지 않는다.
- 2차 세션 발급: Argon2id 검증 뒤 32바이트 무작위 토큰을 생성해 SHA-256 해시만 저장한다. 로그인 시각과 마지막 사용 시각을 같게 시작하며 `expiresAt`은 로그인 시점부터 30일 뒤의 최대 만료 시각이다. 응답에는 `Cache-Control: no-store`를 설정한다. 비동기 비밀번호 검증 중 계정·소속·비밀번호가 바뀔 수 있으므로 저장 트랜잭션에서 다시 확인하고, 저장 실패 시 토큰을 반환하지 않는다.
- 2차 검증: API 추가 전 테스트가 404로 실패하는 것을 확인한 뒤 구현했다. 로그인 E2E 40개를 포함해 전체 E2E 94개, 단위 테스트 17개, 서버 타입 검사·빌드를 통과했다. 실제 Argon2id 검증, 가입→로그인, 다중 세션, DTO 경계값, 계정 상태 변경, 저장 실패 롤백과 Swagger 스키마를 검사했다. 자체 코드리뷰에서 역할·활성 상태 재확인, 토큰 원문 미저장과 오류 응답의 민감 정보 미노출을 점검했다. 테스트는 메모리 DB를 사용했으며 앱·실제 문자 발송·운영 배포 검증은 하지 않았다.
- 3차 인증 API: 공용 `AuthSessionGuard`를 `GET /api/v1/auth/me`와 `POST /api/v1/auth/logout`에 적용했다. `Authorization: Bearer <token>` 헤더만 받으며 쿼리·쿠키의 토큰은 인증에 쓰지 않는다. `me`는 `{ id, email, name, logisticsCompanyId }`를 반환하고 로그아웃은 현재 토큰의 세션만 삭제한 후 204를 반환한다. 이미 폐기된 토큰으로 로그아웃을 반복하면 401이며 요청 본문으로 다른 세션을 지정할 수 없다. Swagger에 opaque Bearer 방식과 한국어 필드 설명을 추가했다. 참고: [NestJS Guard](https://docs.nestjs.com/guards), [Swagger 인증 설정](https://docs.nestjs.com/openapi/security).
- 3차 만료·오류 처리: 서버 시각으로 최대 만료와 마지막 정상 인증 후 7일을 검사하며 경계 시각에 도달하면 만료한다. 정상 인증 시 마지막 사용 시각만 갱신하고, 시계가 되돌아가도 저장된 마지막 사용 시각을 줄이지 않는다. 유효하지 않은 세션은 해당 행을 삭제한 뒤 `401 INVALID_SESSION`으로 거부하며 DB 장애는 `500 INTERNAL_SERVER_ERROR`로 구분한다. 이 검사와 갱신은 하나의 트랜잭션이다. 성공·실패 응답 모두 캐시를 금지한다. 만료 행은 접근 시 정리하며 별도 주기 작업은 추가하지 않았다. 참고: [서버 측 세션 만료 기준](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#automatic-session-expiration).
- 3차 소속 상태: 기존 물류사 비활성화 경로에서 상태 변경과 소속 기사의 모든 세션 삭제를 같은 트랜잭션으로 처리한다. 삭제 실패 시 물류사 상태도 롤백하며 다른 물류사 세션과 기사 데이터는 보존한다. 매 인증 요청에서도 기사 역할·계정·소속 활성 상태를 재확인한다. 앱 화면의 실제 로그아웃 이동은 추후 연동 대상이며 서버 폐기만 구현했다. 어드민 API의 인증·접근 제어는 별도 미구현이므로 이 상태로 외부 배포하면 안 된다.
- 3차 검증: 테스트를 먼저 추가해 누락된 API·세션 폐기로 실패하는 것을 확인한 뒤 구현했다. 세션 E2E 30개를 포함한 전체 E2E 124개, 단위 테스트 17개, 서버 타입 검사·빌드·ESLint를 통과했다. 로그인→세션 확인→로그아웃, 30일·7일 만료 경계, 요청 세션만 갱신·폐기, 소속별 전체 폐기, 상태 변경·시계 역행·DB 실패 롤백과 Swagger를 확인했다. 자체 코드리뷰에서 토큰·사용자 범위, 날짜 비교, 실패 시 응답과 기존 API 계약을 점검했다. 실제 앱·기기·운영 DB·외부 배포는 검증하지 않았다.
- 입력: 이메일, 비밀번호
- 서버 검증: 이메일 형식과 영문·숫자·특수문자를 포함한 8자 이상 비밀번호 정책을 클라이언트와 동일하게 적용
- 성공 결과: 인증 세션을 발급하고 앱이 마일리지 화면으로 이동할 수 있는 응답 제공
- 실패 결과: 입력 오류는 400 `VALIDATION_ERROR`, 미가입 이메일·비밀번호 불일치는 동일한 401 `INVALID_CREDENTIALS`, 비밀번호 확인 후 비활성 계정·소속 또는 검증 중 자격 변경은 403 `ACCOUNT_UNAVAILABLE`, 저장·해시 검증의 내부 오류는 500 `INTERNAL_SERVER_ERROR`로 응답한다. 미가입 이메일도 비교 전용 Argon2id 해시를 검증해 빠른 실패로 계정 유무가 드러나는 것을 줄이며 비교용 계정을 DB에 만들지는 않는다.
- 세션 정책: 앱을 종료한 뒤에도 로그인 유지, 만료 시 로그인 화면으로 이동, 다중 기기 로그인 허용
- 만료 기준: 로그인 시점부터 최대 30일, 마지막 정상 인증 요청부터 미사용 7일 중 먼저 도달하는 시점에 서버가 만료한다. 활동으로 최대 30일 기한을 연장하지 않는다.
- 로그인 시도: 사용자 요청에 따라 횟수 제한과 실패 누적에 따른 계정 잠금을 두지 않는다. 반복적인 비밀번호 대입을 횟수 제한으로 방어하지 않는 위험은 남는다.
- 로그아웃 범위: 일반 로그아웃은 현재 세션만 종료한다. 비밀번호 변경·재설정 성공 시 모든 기기의 기존 세션을 폐기하고 재로그인을 요구한다.
- 소속 상태: 소속 물류사가 비활성 상태(`active=false`)인 기사의 신규 로그인을 차단한다. 비활성화 시 해당 소속 기사의 모든 기존 세션을 즉시 폐기하며, 이미 로그인된 기기도 이후 인증 요청부터 차단한다.
- 후속 작업: 아이디(이메일) 찾기 → 비밀번호 찾기 → 비밀번호 재설정 순서로 서버 기능을 구현한다. 현재 비밀번호를 확인하는 변경 API의 전체 세션 폐기는 구현했으며, 일회용 링크 재설정에도 같은 원자적 폐기가 필요하다. 네이티브 보안 저장소와 앱 세션 복원은 서버 인증 기능들을 마친 뒤 확정·연동한다.

## AUTH-002 회원가입

- 상태: 클라이언트 레이아웃과 서버의 소속 선택·가입·SMS 발송·확인·로그인 API 구현. 다음 서버 구현은 아이디(이메일) 찾기 → 비밀번호 찾기 → 비밀번호 재설정 순서이며, 각 단계에서 테스트·Swagger·코드리뷰를 수행한다. 앱의 실제 요청 연결은 이 기능들을 마친 뒤 진행하고 그전까지는 서버 연동 대기 안내를 유지한다.
- 입력: 이메일, 비밀번호, 소속, 성함, 연락처, 문자 인증번호, 필수·선택 약관 동의
- 계정 검증: 이메일 중복 확인, 연락처 중복 확인, 서버 측 비밀번호 정책 검증과 안전한 비밀번호 해시 저장
- 소속 목록: `GET /api/v1/logistics-companies`가 활성 소속의 식별자·명칭만 제공한다. 소속별 서비스 가격·이용 기간 계약은 별도다.
- 휴대폰 인증: 유효한 연락처로 SOLAPI SMS 6자리 인증번호를 발송한다. 인증번호는 접수 성공 후 3분간 유효하며 재발송 요청은 이전 번호와 증명을 즉시 무효화한다. 재발송이 실패해도 이전 증명을 복구하지 않는다. 재발송 대기, 발송 요청 횟수와 검증 시도 횟수 제한은 두지 않는다. 별도 확인 요청이 성공하면 `verificationProof`를 발급하고, 가입 요청은 이 증명을 필수로 검증한다.
- API: `POST /api/v1/auth/phone-verifications`는 `{ phone }`을 받아 `{ verificationId, expiresAt }`를 반환한다. `POST /api/v1/auth/phone-verifications/:verificationId/confirm`은 `{ code }`를 받아 `{ verificationProof, expiresAt }`를 반환한다. `purpose`를 생략하면 기존 `sign_up` 계약이며, 다른 목적은 명시해야 한다. 가입 증명은 찾기·연락처 변경에 사용할 수 없다.
- 증명 보안: 인증번호는 인증 식별자에 묶인 HMAC으로, 무작위 증명은 SHA-256 해시로만 저장한다. 확인 시 원래 만료 시각을 연장하지 않으며 한 번 확인한 번호로 증명을 다시 발급하지 않는다. `POST /api/v1/auth/signup`은 해당 휴대폰의 유효한 증명을 가입 트랜잭션에서 한 번만 소비한다.
- 발송 경계: HTTP 200만으로 성공 처리하지 않고 SOLAPI의 메시지별 접수를 확인한다. 발송 대기·실패 레코드는 사용할 수 없고, 재발송으로 무효화된 요청은 늦게 성공 응답이 와도 다시 활성화하지 않는다. 타임아웃 후 자동 재발송은 하지 않는다. 실제 문자 수신까지 보장하는 응답은 아니다.
- 약관: 필수 약관 동의 여부와 선택 마케팅 동의를 가입 시점의 약관 버전과 함께 저장하는 정책 필요
- 성공 결과: 가입 완료 응답 후 안내 메시지를 표시하고 로그인 화면으로 이동
- 실패 결과: 이메일·연락처 중복, 인증번호 불일치·만료와 일시적 서버 오류를 구분할 오류 계약 필요
- 설정: 서버 `.env.example`의 SOLAPI API 키·Secret·사전 등록 발신번호와 별도의 인증번호 HMAC 비밀값을 설정한다. 누락 시 발송 성공이나 증명을 만들지 않는다. 새 SMS SDK나 DB 테이블은 추가하지 않았다.
- 검증: 외부 SOLAPI HTTP만 모의 처리한 발송·확인·가입 E2E를 추가했다. 실제 키·발신번호를 사용한 문자 수신과 앱 연동은 아직 검증하지 않았다.
- 결정 필요: 이메일 인증 여부, 약관 상세 문서 경로

## AUTH-003 이메일 찾기

- 상태(2026-09-08): 목적별 SMS 발송·확인과 이메일 조회 결과 API를 서버에 구현했다. 앱 연동은 하지 않았다.
- 결과 API: `POST /api/v1/auth/find-email { phone, verificationProof }`는 `find_email` 목적·연락처에 묶인 유효한 증명을 한 번 소비하고 `{ maskedEmail, phoneLastFour }`를 반환한다. 가입 연락처 끝 4자리 외 원문 이메일·이름·식별자는 반환하지 않는다. 미가입·탈퇴·관리자 계정은 동일한 `404 ACCOUNT_NOT_FOUND`이며 이때도 증명을 소비한다. 물류사 비활성화는 로그인 제한이므로 기사 이메일 조회 자체는 유지한다. 잘못된 증명은 `400 PHONE_VERIFICATION_INVALID`, 입력 오류는 `400 VALIDATION_ERROR`, DB 장애는 `500 INTERNAL_SERVER_ERROR`로 구분한다.
- 결과 검증·리뷰(2026-09-08): 메인 단위 21개·전체 E2E 371개(신규 이메일 찾기 25개)·타입 검사·비수정 린트·빌드·diff 검사 통과. 두 읽기 전용 리뷰어는 관련 E2E 118개·146개와 별도 메모리 DB의 소비 후 조회 실패 롤백을 확인했으며 차단 지적은 없었다. 메인이 서버 구현·검증했고 사용자는 마스킹·문구를 승인했다. 실제 SMS·앱 연동은 검증하지 않았다.
- SMS 계약: 기존 `POST /api/v1/auth/phone-verifications`와 `/:verificationId/confirm`에 `purpose: find_email`을 지정한다. 증명은 목적과 휴대폰에 묶이며 회원가입에 사용할 수 없다. `purpose` 생략 시 기존 `sign_up` 계약을 유지한다.
- 검증·리뷰(2026-09-08): 메인 서버 타입 검사·비수정 린트·빌드, 단위 17개·전체 E2E 197개 통과. 포트 제한으로 실패한 E2E는 임시 로컬 포트 권한 후 재실행했다. 두 독립 리뷰어가 SMS·가입 E2E 51개를 각각 실행했으며 타목적 증명 거부 테스트가 물류사 오류로도 통과할 수 있는 문제를 발견해 `PHONE_VERIFICATION_INVALID` 코드까지 검증하도록 보완했다. 보안 리뷰어는 메모리 DB 저장·활성화·증명 저장 실패 검사도 수행했다. 실제 SMS 발송·프런트 연동은 하지 않았다.
- 입력: 연락처, 문자 인증번호
- 본인 확인: 유효한 연락처만으로 인증번호 발송을 요청한다. 별도 인증번호 확인 요청이 성공하면 `verificationProof`를 발급하고, 이 증명이 있을 때만 이메일 조회를 허용한다.
- 휴대폰 인증: SOLAPI SMS 6자리 인증번호는 3분간 유효하며 재발송하면 이전 번호를 즉시 무효화한다. 재발송 대기, 발송 요청 횟수와 검증 시도 횟수 제한은 두지 않는다.
- 성공 결과: 가입 연락처 끝자리와 마스킹된 이메일만 반환한다. 사용자가 승인한 마스킹은 `@` 앞 2자만 노출하고 나머지를 `*`로 가리며, 2자 이하면 전부 가리는 방식이다. 앱이 원문 이메일이나 계정 존재 여부를 추측해 만들지 않는다.
- 실패 결과: SMS 인증 후 조회 결과가 없으면 `일치하는 회원정보를 찾을 수 없습니다.`로 안내한다. 인증번호 불일치·만료와 일시적 서버 오류를 미가입 결과로 바꾸지 않는다.
- 결정 필요: 추가 감사 로그·개인정보 마스킹 정책. 확정되지 않은 로그 기능은 추가하지 않는다.

## AUTH-004 비밀번호 재설정

- 상태(2026-09-08): `purpose: reset_password` SMS 발송·확인과 계정 일치 확인·Postmark 메일 요청·토큰 발급/소비를 서버에 구현했다. 발송 시 `email`과 `phone`이 모두 필요하고 증명은 해당 조합에 묶인다. 실제 발신 설정과 앱 연동은 미완료이며 SMS 성공만으로 계정 복구를 완료 처리하지 않는다.
- 재설정 소비(2026-09-08): `POST /api/v1/auth/reset-password`에 `{ token, newPassword }`를 보내면 DB의 유효한 기사 토큰을 SHA-256으로 조회하고 Argon2id 저장·본인 전체 세션 폐기·기존 미사용 링크 소비를 원자적으로 처리한다. 성공은 본문 없는 `204`, 입력 오류는 `400 VALIDATION_ERROR`, 만료·재사용·알 수 없는 토큰·사용 불가 계정은 `400 PASSWORD_RESET_INVALID`, 해시/저장 실패는 `500 INTERNAL_SERVER_ERROR`다. 인증 응답은 `no-store`다. 후속 Postmark 발급 API까지 서버에 구현했지만 실제 메일 설정·수신과 앱 연동을 검증하기 전까지 사용자 이메일 복구 전체 흐름은 부분 완료다.
- 검증·리뷰(2026-09-08): 메인 타입 검사·린트·빌드·단위 17개·전체 E2E 224개 통과. 새로운 재설정 27개는 유효 토큰·타인 세션 보존·동시 소비·해시 중 자격 변경·해시 실패·비밀번호/토큰/세션 저장 실패 롤백·Swagger를 검증했다. 두 독립 리뷰어가 관련 E2E 128개를 각각 통과했고 기능 리뷰어는 재사용 DTO 검증 9개도 별도 확인했다. 미해결 차단 지적은 없다. 기존 DB 테이블의 Drizzle 매핑만 추가했으며 개발 DB 초기화·실제 메일 발송은 수행하지 않았다.
